# REQ-NF-001: Безопасность хранения паролей

## Описание

Система НИКОГДА не должна хранить пароли пользователей в открытом виде. Все пароли должны быть захешированы с использованием современных криптографических алгоритмов.

Это критически важное требование безопасности, которое защищает пользователей в случае утечки базы данных.

## Критерии приемки

- [ ] Пароли хешируются с использованием bcrypt (или аргон2)
- [ ] Cost factor для bcrypt не менее 10
- [ ] Каждый пароль имеет уникальную соль (salt)
- [ ] В базе данных хранится только хеш, никогда не оригинальный пароль
- [ ] В логах никогда не выводятся пароли (даже при ошибках)
- [ ] При отправке данных на сервер пароль передается через HTTPS
- [ ] Невозможно восстановить оригинальный пароль из хеша
- [ ] При смене пароля создается новый хеш (не изменяется старый)

## Обоснование

По статистике, при утечках баз данных большинство пользователей страдает именно из-за хранения паролей в открытом виде или с использованием слабого хеширования (MD5, SHA1).

Современные стандарты безопасности (OWASP, NIST) требуют использования специализированных алгоритмов хеширования паролей с солью.

## Технические заметки

### Рекомендуемая реализация:

```javascript
// Пример для Node.js с bcrypt
const bcrypt = require('bcrypt');
const saltRounds = 10;

// При регистрации
const passwordHash = await bcrypt.hash(plainPassword, saltRounds);

// При входе
const isValid = await bcrypt.compare(plainPassword, passwordHash);
```

### Альтернативы:
- Argon2 (более современный, но менее распространенный)
- PBKDF2 (приемлемо, но bcrypt предпочтительнее)

### НЕ использовать:
- MD5 (взломан)
- SHA1 (взломан)
- SHA256 без соли (недостаточно)

## Тестирование

### Тесты безопасности:
- Проверить что в БД хранятся только хеши
- Проверить что невозможно восстановить пароль из хеша
- Проверить что каждый хеш уникален (даже для одинаковых паролей)
- Проверить что в логах нет паролей

### Пентесты:
- Попытка SQL инъекции для получения паролей
- Анализ сетевого трафика (пароль должен передаваться по HTTPS)

## Риски

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Разработчик случайно логирует пароль | Medium | High | Code review, автоматические проверки в CI/CD |
| Использование слабого алгоритма | Low | Critical | Указать конкретный алгоритм в документации |
| Передача пароля по HTTP | Low | Critical | Принудительное использование HTTPS на уровне сервера |

## Compliance

Это требование необходимо для соответствия:
- GDPR (защита персональных данных)
- PCI DSS (если будут платежи)
- ISO 27001 (стандарты информационной безопасности)
